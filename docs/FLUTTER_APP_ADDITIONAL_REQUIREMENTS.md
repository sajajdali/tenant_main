# مشخصات تکمیلی Flutter: ورود، عضویت و خرید پکیج

این سند قرارداد اجرایی نسخه Flutter (Android و وب اپلیکیشن) است. APIهای مرجع در Swagger با tagهای `Customer App Auth`، `Membership` و `Package Purchase` هستند. نام سرویس پشت پرداخت در هیچ سطحی از Flutter نمایش داده یا فرض نمی‌شود؛ در این سند فقط از «درگاه پرداخت آنلاین» استفاده شده است.

## 1. ورود با رمز یک‌بارمصرف (OTP)

### API

1. کاربر شماره را وارد می‌کند و Flutter درخواست زیر را می‌زند:

   `POST /api/v1/app/auth/login`

   ```json
   { "mobile": "09123456789" }
   ```

2. پاسخ موفق، زمان اعتبار و زمان باقی‌مانده تا ارسال مجدد را برمی‌گرداند. در محیط واقعی `data.code` همیشه `null` است؛ فقط اگر `data.testMode=true` بود ممکن است کد تست برگردد. این مقدار صرفاً برای توسعه است، نه UI تولید.
3. پس از چهار رقم، Flutter درخواست زیر را می‌زند:

   `POST /api/v1/app/auth/verify`

   ```json
   { "mobile": "09123456789", "code": "1234", "deviceName": "android-app" }
   ```

4. `accessToken` دریافتی در ذخیره‌سازی امن نگهداری و در همه درخواست‌های حفاظت‌شده با `Authorization: Bearer <token>` ارسال شود.

### پرشدن خودکار کد، بدون حذف ورود دستی

- Android: از SMS Retriever API استفاده شود؛ اگر در دسترس نبود، SMS User Consent. متن پیامک باید شامل OTP چهاررقمی و app hash موردنیاز SMS Retriever باشد. اپ نباید permission گسترده خواندن SMS درخواست کند.
- وب: در مرورگرهای پشتیبان از WebOTP API و قالب استاندارد origin-bound SMS استفاده شود. در مرورگرهای پشتیبان‌نشده، هیچ خطایی نمایش ندهید.
- در هر دو پلتفرم، کد استخراج‌شده فقط در input قرار می‌گیرد. در صورت تکمیل چهار رقم می‌توان verify را خودکار ارسال کرد؛ ورود دستی، paste، و دکمه تأیید باید همیشه کار کنند.
- کد را در URL، log، crash report، analytics، clipboard یا پیام خطا ننویسید. timer پاسخ سرور، معیار فعال‌شدن «ارسال مجدد» است.

## 2. مرحله «سوابق بیماری» در عضویت اولیه

Endpoint: `POST /api/v1/app/membership/medical-conditions`

گزینه «بیماری خاصی ندارم» و دکمه «ادامه» هر دو باید همان نتیجه را ایجاد کنند:

```json
{ "medicalConditionsItems": [] }
```

رفتار دقیق UI:

- با لمس «بیماری خاصی ندارم»، گزینه انتخاب، loading کوتاه نشان داده، درخواست بالا ارسال و در موفقیت به مرحله بعد بروید.
- با وجود انتخاب‌نشدن بیماری، دکمه «ادامه» فعال است. لمس آن دقیقاً payload خالی بالا را می‌فرستد.
- اگر بیماری اضافه شده باشد، «ادامه» لیست کامل `medicalConditionsItems` را ارسال می‌کند.
- تا پایان درخواست، tapهای تکراری را غیرفعال کنید؛ در خطا در همان مرحله بمانید و امکان تلاش مجدد بدهید.

این رفتار مانع از آن می‌شود که کاربر با زدن دکمه ادامه تصور کند دکمه خراب است.

## 3. انتخاب و خرید پکیج

در صفحه پکیج، لمس خود کارت/آیتم پکیج باید مسیر خرید همان پکیج را شروع کند؛ کاربر نباید مجبور به لمس «ادامه» یا «مشاهده فاکتور» باشد. این دو CTA حذف نشوند، اما عملکردشان همان انتخاب فعلی و شروع خرید باشد تا صفحه از نظر بصری ناقص نشود.

ترتیب عملیات:

1. با tap روی کارت، `POST /api/v1/app/nutrition/package-checkout/preview` با `nutrition_package_id` را بزنید و قیمت نهایی/تخفیف و روش‌های قابل استفاده را نشان دهید.
2. اگر Android واقعاً از کافه بازار نصب شده و `settings.cafebazaarEnabled=true` است، فقط جریان IAP کافه بازار را اجرا کنید.
3. در تمام حالت‌های دیگر (وب اپلیکیشن و Android غیرِبازار)، `POST /api/v1/app/nutrition/package-checkout/pay` را بزنید.
4. اگر پاسخ `data.mode="sandbox"` بود، خرید کامل شده است؛ summary را تازه‌سازی کنید.
5. اگر `data.mode="gateway"` بود، `data.paymentUrl` اجباری است. همان URL را باز کنید؛ بس.

### قرارداد پرداخت آنلاین

Flutter و وب اپلیکیشن نباید نام، SDK، callback، توکن یا فرم هیچ درگاه پرداخت آنلاینی را بدانند یا پردازش کنند. سرور مسئول ساخت سفارش، تولید URL کامل HTTPS، نگهداری هر داده POST لازم و انتقال به درگاه است.

```text
Flutter/Web -- POST /pay --> سرور
Flutter/Web <-- paymentUrl -- سرور
Flutter/Web -- بازکردن paymentUrl --> صفحه واسط امن سرور --> درگاه پرداخت آنلاین
درگاه --> GET callback سرور --> verify سمت سرور --> صفحه وب نتیجه پرداخت
صفحه نتیجه --> «بازگشت به اپلیکیشن» --> Flutter/Web
```

- `paymentUrl` را با external browser یا WebView باز کنید. برای Android، browser سیستم یا Custom Tab ترجیح دارد تا بازگشت deep link مطمئن باشد.
- Flutter جدید `redirectForm` را پردازش نمی‌کند؛ این فیلد فقط سازگاری نسخه‌های قدیمی است.
- بازکردن URL به معنی موفق‌بودن خرید نیست. تنها status نهایی سرور و refresh summary معتبر است.
- درگاه بازار یک مسیر مستقل است؛ فعال بودنش نباید پرداخت آنلاین وب را پنهان یا غیرفعال کند.

## 4. callback، صفحه نتیجه و بازگشت به اپلیکیشن

مسیر callback سرور:

`GET /nutrition-package-payments/{order}/callback`

این endpoint فقط مقصد بازگشت درگاه است؛ Flutter آن را صدا نمی‌زند. سرور تراکنش را مستقلاً verify می‌کند و سپس با redirect به این صفحه وب می‌رود:

`GET /nutrition/membership/package-result?status=success&order=...&invoice=...&reference=...&endsAt=...`

یا در خطا:

`GET /nutrition/membership/package-result?status=failed&tracking=...`

نیازمندی صفحه وب نتیجه:

- وضعیت موفق/ناموفق/درانتظار، شماره سفارش یا پیگیری غیرحساس و پیام مناسب را نشان دهد.
- یک دکمه روشن «بازگشت به اپلیکیشن» داشته باشد.
- دکمه deep link ثبت‌شده برنامه را باز کند (مثلاً `yourapp://payment-result?order=45`) و اگر اپ نصب/قابل بازشدن نبود، همان صفحه وب باقی بماند. query صفحه نتیجه منبع تأیید پرداخت نیست.
- پس از بازگشت به اپ، Flutter باید `GET /api/v1/app/nutrition/package-checkout/summary` را بزند و از وضعیت سفارش/اشتراک سرور UI را به‌روزرسانی کند.

## 5. کنترل خطا و idempotency در Flutter

- هنگام ارسال `/pay` loading نمایش دهید و تا دریافت پاسخ، همان خرید را دوباره ارسال نکنید.
- اگر اپ هنگام پرداخت بسته شد یا کاربر از مرورگر برگشت، با بازشدن دوباره اپ summary را refresh کنید؛ «پرداخت ناموفق» را صرفاً از برگشت کاربر نتیجه نگیرید.
- 401: ورود مجدد. 422: پیام سرور را نشان دهید؛ اگر به `replace_active_subscription=true` نیاز بود، تأیید شفاف کاربر بگیرید و سپس همان درخواست را تکرار کنید.
- پرداخت موفق، پکیج قبلی را تمدید نمی‌کند: اشتراک فعال قبلی منقضی و پکیج جدید از تاریخ خرید شروع می‌شود.
